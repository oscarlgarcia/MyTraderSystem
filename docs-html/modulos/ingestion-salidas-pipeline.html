Proposito

Explicar que produce ingestion, donde se persiste y quien lo consume. Esta pagina es util tanto para operar como para entender el contrato con features y el resto del pipeline.

Handoff principal al pipeline

El contrato mas importante es la lista de IngestionEvent devuelta por run_ingestion_service(). Esa lista se entrega a run_feature_pipeline() y sirve como materia prima del resto del ciclo de decision.

Alertas y significados operativos

El runbook ya fija un conjunto minimo de alertas: reconnect_storm, gap_detected, gap_irreparable, heartbeat_missed, dlq_spike, sink_failure, compaction_backlog_high y compaction_failure_detected. La UI las presenta como alertas abiertas/acked y el operador debe interpretarlas junto a recommended_action.

Que no entrega ingestion

  • No entrega por si mismo decisiones de trading; solo datos y senales operativas.
  • No garantiza promotion a live: eso depende de readiness, gates y runbooks.
  • No entrega dashboards externos en el repo; solo eventos, logs y artefactos versionables o runtime-locales.
