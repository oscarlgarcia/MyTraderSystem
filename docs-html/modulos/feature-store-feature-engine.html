Modulo Feature Store / Feature Engine

Catalogo, calculo, almacenamiento y serving de features para research, backtesting, paper y live.

Inicio / Modulos / Modulo Feature Store / Feature Engine

Proposito

Definir la capa de features como plataforma operativa y no solo como calculo puntual. El modulo ya combina definiciones versionadas, runtime incremental, offline store, online store, catalogo consultable y contratos de serving que permiten seleccionar bundles y razonar sobre su compatibilidad con distintas familias de estrategia.

Resumen ejecutivo del cambio

  • Se introdujo un catalogo canonico con 112 features registradas por familia, estrategia, fuente, fase y estado.
  • Se formalizaron taxonomias de feature families, strategy families y source scopes dentro del propio codigo.
  • El runtime default paso a publicar ventanas 3, 5, 10, 20, 50 con agregadores sma, ema, max y min.
  • El gap operativo entre la estrategia basica y el producer default se redujo publicando sma_3 y manteniendo fallback a sma_5 en la vista de estrategia.
  • Se anadio discovery HTTP y CLI para listar features por familia, estrategia, fase, fuente o bundle.

Capas reales del modulo

Catalogo

app/features/catalog.py define la taxonomia comun de la plataforma. Cada FeatureCatalogEntry registra nombre, familia, familias de estrategia, fuentes requeridas, fase, bundle, inputs, lookback, warmup, targets y estado.

Definitions y bundles

FeatureDefinition y FeatureSetDefinition siguen siendo el contrato de calculo, pero ahora se apoyan en bundles explicitos como core_market_bundle, trend_bundle o portfolio_risk_bundle.

Runtime incremental

app/features/runtime.py mantiene el calculo incremental con semantica temporal, watermarks y recompute controlado. El default usa el bundle runtime ampliado definido en app/features/bundles.py.

Stores

Offline y online store siguen siendo la base de materializacion y serving. El cambio nuevo no los reemplaza: los ordena alrededor de bundles, catalogo y versiones explicitas.

Discovery

app/features/api.py expone endpoints de descubrimiento y scripts/feature_catalog.py permite consultar el catalogo sin tocar el codigo.

La lectura correcta es esta: el catalogo ya es canonico, pero el estado implemented solo marca el subconjunto cuya semantica, naming y wiring quedan hoy cerrados en codigo. El runtime legacy expandido sigue calculando aliases operativos como max_* y min_*, pero el baseline catalogado como implemented se ha limitado de momento a price.last, ret.log.1s y medias trend.

Runtime default actual

El runtime default ya no se comporta como un set minimo opaco. El bundle default definido en app/features/bundles.py usa ventanas 3, 5, 10, 20, 50 y agregadores sma, ema, max, min. En la practica, el producer publica aliases como price, ret_1, sma_3, sma_5, ema_20, max_50 o min_10 en un mismo contrato runtime.

La estrategia basica sigue consumiendo price, ret_1 y sma_3. Para mantener compatibilidad, la vista de estrategia hace fallback de sma_3 a sma_5 cuando no exista el primer alias.

Discovery y consulta

CLI

El comando python scripts/feature_catalog.py permite listar nombres o entradas completas filtrando por familia, fase, estrategia, fuente, estado o bundle.

HTTP API

El feature API ahora expone /catalog/features, /catalog/families, /catalog/strategy-families, /catalog/source-scopes y /catalog/bundles.

Uso recomendado

Research, backtesting y serving deben consultar el catalogo o sus bundles antes de asumir que un feature esta disponible. El objetivo es que la compatibilidad deje de depender de convenciones implicitas o tests que inyectan columnas a mano.
