Lectura verificada del modulo

El modulo visible hoy no es un backoffice conectado al runtime en caliente, sino un control plane web interno desacoplado para operar ingestion. El patron implementado es Hot Path -> JSONL Telemetry Sink -> Read Model SQLite -> FastAPI/Jinja2 -> UI, con un worker separado para comandos asincronos.

Flujo de lectura de la UI

  1. El operador entra por /ui/overview o cualquier otra ruta HTML servida por webUI.
  2. Antes de consultar la vista, la API llama a builder.sync_once().
  3. El builder procesa solo lineas nuevas de los JSONL gracias a read_model_offsets.
  4. Los eventos nuevos se materializan en SQLite del control plane.
  5. La plantilla Jinja consulta el snapshot agregado desde SQLite y renderiza HTML.

Este flujo mantiene la UI sobre un read model derivado y evita inspeccionar memoria, dedup windows o colas del ingestion engine.

Flujo de comandos asincronos

  1. La UI hace POST a /api/commands/ack-alert, /api/commands/resync o /api/commands/replay.
  2. La API inserta una fila pending en command_requests y anade auditoria de encolado.
  3. control-plane-worker reclama el siguiente comando, lo marca running y ejecuta la operacion correspondiente.
  4. Al terminar, el worker marca succeeded o failed y persiste command_audit.
  5. El worker emite ademas recovery_command_audit en el telemetry path para trazabilidad externa.

Operativamente, la cola no convierte un feed no soportado en feed soportado: resync y replay ayudan a paper y a live kline, pero no cierran por si solos el gap estructural de trade o book para live.

Guia operativa complementaria

La explicacion orientada a usuario de la UI y de como navegarla se mantiene ahora en UI y operacion del control plane. Esta pagina conserva el foco mas tecnico sobre arquitectura, read model, cola y worker.

Dependencias y despliegue observables

  • docker-compose.yml define dos servicios de control plane separados: webUI y control-plane-worker.
  • Ambos comparten bind mount del repo y el volumen .venv con el servicio app.
  • webUI publica 8001:8001 y ejecuta python -m app.controlplane.api.
  • control-plane-worker ejecuta python -m app.controlplane.worker y consume la cola SQLite.
  • La relacion entre engine, UI y worker es principalmente por filesystem compartido: JSONL de telemetria, refs de checkpoints y SQLite de control plane.

Huecos conocidos

  • Las plantillas hablan de polling, pero la v1 no implementa aun auto-refresh HTMX por hx-get; el refresco principal sigue siendo por navegacion o recarga.
  • No hay autenticacion fuerte, RBAC ni multiusuario; el valor por defecto del operador es ui-operator.
  • La implementacion PostgreSQL aun es un stub reservado y no puede desplegarse.
  • No se exponen logs live ni raw market data desde la UI, por diseno.
  • La UI no sustituye la observabilidad externa exigida por gates; el contrato operativo sigue requiriendo surfaces de runtime, alerts, logs y promotion fuera de la propia web.
