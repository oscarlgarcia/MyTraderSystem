Proposito

Explicar de forma util para usuarios y operadores como se arranca ingestion, que hace internamente, que muestra su UI, que artefactos deja y como se valida antes de paper o live.

Flujo operativo resumido

  1. El usuario lanza ingestion desde CLI o desde el runtime integrado con python -m app.
  2. La configuracion se carga desde app.config y fija entorno, rutas, endpoints y politicas de runtime.
  3. El pipeline consume eventos del vendor o de fixtures, los valida, deduplica y persiste en raw/normalized.
  4. El runtime emite summaries, health y alertas al telemetry path desacoplado.
  5. El control plane materializa un read model en SQLite y lo expone via UI web.
  6. El resto del pipeline recibe IngestionEvent ya normalizados para features y decision.
  7. La readiness se cierra con tests, canaries, soak, benchmark y release gates.

UI y operaciones disponibles

La UI actual no consulta memoria viva del runtime. Lee un read model SQLite generado desde telemetria JSONL. Esto permite inspeccionar runs, streams, alerts, checkpoints y comandos de recovery sin acoplar el hot path a la web.

  • Overview: resume ejecuciones, streams degradados, alertas abiertas y comandos pendientes.
  • Streams: expone scopes y su severidad operativa.
  • Recovery: encola resync, replay range y replay de quarantine.
  • Audit: muestra la auditoria de comandos del control plane.

La guia operativa completa esta en UI y operacion del control plane.

Salidas que consume el resto del sistema

El punto de integracion principal es la lista de IngestionEvent que devuelve run_ingestion_service() hacia app.main.run_cycle(). Ademas, ingestion deja logs estructurados, summaries, health, alertas y artifacts que sirven tanto al pipeline principal como a la operacion.

Detalle completo en Salidas del modulo hacia el pipeline.

Tests y validacion

La cobertura del modulo no se limita a unitarios. El repo incluye contratos de runtime y storage, replay parity, checkpoints, resiliencia, control plane, canaries, soak, benchmark y release gates. La validacion actual separa explicitamente evidencia de replay para paper trade frente a evidencia de runtime para paper/live kline. La guia detallada de suites, objetivos y artefactos esta en Tests, readiness y validacion.
