Proposito

Explicar de forma util para usuarios y operadores como se arranca ingestion, que hace internamente, que artefactos deja y como se valida antes de paper o live. Desde esta iteracion la pagina tambien cubre el nuevo bloque de gobierno de datasets, serving curado y superficies consumidoras asociadas.

Gobierno del dato y serving introducidos en esta iteracion

El modulo ya no termina en raw y normalized. Sobre esa base ahora materializa artefactos de gobierno y superficies consumidoras:

  • Contracts: dataset-contracts.json valida la particion normalized, fija approved targets y ahora adjunta dataset_version y lineage_id.
  • Catalogo: datasets.json resume existencia, calidad, promotion y versionado reproducible por particion.
  • Quality: dataset-quality.json, dataset-incidents.jsonl y dataset-service-levels.json convierten integridad, freshness y breaches operativos en una señal consumible.
  • Gap closure: gap-fill-plan.json deja visibles las ventanas detectadas y el cierre pendiente o ejecutado por control plane.
  • Capabilities y delivery: venue-capabilities.json y delivery-contracts.json hacen explicita la capacidad operativa del feed, incluido si soporta hot subscriptions o bootstrap por snapshot.
  • Serving consumible: query historica, curated store, snapshot service, replay service y publication bus desacoplan a los consumers del layout interno de parquet y ahora preservan dataset_id, dataset_version y lineage_id.
  • Lifecycle: storage-lifecycle.json y storage-lifecycle-actions.json fijan tiering, acciones ejecutadas y derivados livianos por downsampling.

Cierre operativo estandar

El cierre operativo ya no se ejecuta ensamblando scripts manualmente. El comando base es poetry run python scripts/ingestion_operational_cycle.py, que lanza readiness por perfil, persiste la verificacion de observabilidad externa y deja un manifest auditable del ciclo. Los playbooks markdown que fijan el caso estandar quedan en docs/operations/ingestion_operational_closure_paper.md y docs/operations/ingestion_operational_closure_live.md.

Reglas operativas ya fijadas en codigo: execution_ref y channel son obligatorios, el cierre final solo acepta scheduled o pipeline, y cualquier intento con book debe terminar en NO-GO. El ciclo tambien exige governance del runner con schedule_name, job_id, job_url, owner, cadence_state y context_source; el runner puede resolverse por CLI, JSON persistido o entorno. La observabilidad externa puede inyectarse por surface_manifest, pero el cierre final requiere artifact persistido.

Flujo operativo resumido

  1. El usuario lanza ingestion desde CLI o desde el runtime integrado con python -m app.
  2. La configuracion se carga desde app.config y fija entorno, rutas, endpoints y politicas de runtime.
  3. El pipeline consume eventos del vendor o de fixtures, los valida, deduplica y persiste en raw/normalized.
  4. El runtime emite summaries, health y alertas al telemetry path desacoplado.
  5. El control plane materializa un read model en SQLite y, ademas, puede refrescar catalogo, quality, curated serving, subscriptions, publication y benchmarks.
  6. Research y backtesting consumen query historica o replay sin depender del layout interno de parquet.
  7. Paper/live pueden bootstrapearse via snapshot service y latest curado antes de consumir incrementales o publication bus.
  8. El cierre operativo estandar usa scripts/ingestion_operational_cycle.py, que resuelve el runner desde CLI, JSON o entorno, pasa surface_manifest a readiness y persiste ingestion_operational_governance_*.json, ingestion_operational_history_*.jsonl, ingestion_observability_verification_*.json, ingestion_operational_evidence_*.json y ingestion_release_gates_*.json con provenance obligatoria.
  9. Un run live real puede terminar correctamente en NO-GO aunque la suite del repo este verde si el runtime detecta gaps, degradacion de streams o recovery insuficiente.

UI y operaciones disponibles

La UI actual no consulta memoria viva del runtime. Lee un read model SQLite generado desde telemetria JSONL. Esto permite inspeccionar runs, streams, alerts, checkpoints y comandos de recovery sin acoplar el hot path a la web. Desde esta iteracion la API del control plane tambien expone catalogo, calidad, incidents, service levels, gap fill plan, query, snapshot, replay report y future scope sobre los nuevos artefactos de market data.

  • Overview: resume ejecuciones, streams degradados, alertas abiertas y comandos pendientes.
  • Streams: expone scopes y su severidad operativa.
  • Recovery: encola resync, replay range, replay de quarantine y ahora tambien gap-fill.
  • Catalog refresh: materializa catalogo, contracts, quality, service levels, capabilities, delivery, lifecycle y plan de huecos.
  • Serving refresh: actualiza marketdata.sqlite y publication bus, preservando versionado y lineage.
  • Subscriptions: persiste cambios de symbols y stream types y el runtime los recoge mediante reconnect controlado por revision.
  • Audit: muestra la auditoria de comandos del control plane.

La guia operativa completa esta en UI y operacion del control plane.

Salidas que consume el resto del sistema

El punto de integracion principal es la lista de IngestionEvent que devuelve run_ingestion_service() hacia app.main.run_cycle(). Ademas, ingestion deja logs estructurados, summaries, health, alertas y artifacts que sirven tanto al pipeline principal como a la operacion.

Tests y validacion

La cobertura del modulo no se limita a unitarios. El repo incluye contratos de runtime y storage, replay parity, checkpoints, resiliencia, control plane, canaries, soak, benchmark y release gates. La validacion actual separa explicitamente evidencia de replay para paper trade frente a evidencia de runtime para paper/live trade y paper/live kline. El cierre operativo se consolida en ingestion_operational_evidence*.json, no solo en el resultado de pytest: el gate ya exige un artefacto persistido, con provenance.source, runner_id, trigger, generated_by y derived_in_process = false, ademas de surfaces externas verificables.

La guia detallada de suites, objetivos y artefactos esta en Tests, readiness y validacion.

Limitaciones verificadas

  • Scope paper soportado hoy

    trade, kline

    trade en paper queda respaldado por evidence de replay y parity, no por runtime live.

  • Scope live soportado hoy

    trade, kline

    trade y kline quedan soportados en live; trade exige exact recovery e handoff, mientras book sigue excluido.

  • Superficies externas minimas

    ingestion.<target>.runtime, alerts, logs, promotion

    Cada surface debe declarar owner, surface_ref, verification_mode, verified_at y verification_ref; para live se exige ademas ingestion.live.cutover.
