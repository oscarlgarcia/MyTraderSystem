Serving, Query y Snapshots de Market Data

Superficies consumibles para research, backtesting, paper y el bootstrap de consumidores.

Inicio / Datos / Serving, Query y Snapshots de Market Data

Proposito

Explicar las superficies nuevas que desacoplan a los consumidores del almacenamiento raw y normalized interno. Esta pagina documenta query historica, serving curado, snapshot service, replay service, publication bus y contratos de entrega.

Query historica

La query historica trabaja directamente sobre particiones normalized y no sobre raw. El contrato visible hoy es un request por env, stream_type, symbol, venue, start_ts, end_ts y limit. La respuesta devuelve filas canonicamente normalizadas con sus clocks, lineage y metadata ya preservados.

  • Casos de uso: research reproducible, backtesting, validacion puntual de incidents, refresh del serving curado.
  • Limite actual: la query itera particiones normalized del filesystem; no es todavia un servicio distribuido ni indexado para alta concurrencia.
  • Ventaja: evita que un consumidor de research o backtesting conozca el layout interno de Parquet.

Serving curado y low-latency path

La capa CuratedServingStore mantiene una tabla latest_events con la ultima fila conocida por env, venue, stream_type y symbol. Ademas registra refresh_audit para dejar trazabilidad del refresh, numero de filas leidas y latest_exchange_ts.

ArtefactoRutaRol
Serving DBdata/<env>/serving/marketdata.sqliteLectura operativa de ultimo estado curado.
Tabla latest_eventsSQLiteUltimo evento por simbolo y feed.
Tabla refresh_auditSQLiteHistorial de refresh del serving.

Esta capa no sustituye al normalized store como fuente de verdad historica. Su funcion es desacoplar el bootstrap y los reads operativos del scan directo a Parquet.

Snapshot service

El SnapshotService aplica una politica simple y explicita: preferir curated, luego caer a query historica. Esto reduce el tiempo de bootstrap cuando el serving ya fue refrescado, sin perder la capacidad de reconstruir el ultimo estado desde normalized si la capa curada aun no esta caliente.

  • Request: env, stream_type, symbol, venue, prefer_curated.
  • Respuesta: fila normalizada mas reciente para ese scope.
  • Uso tipico: consumidores paper/live que necesitan un latest consistente antes de escuchar incrementales o leer publication bus.

Replay service

El replay ya existia como primitiva interna, pero ahora se documenta y se expone como superficie consumible mediante ReplayServiceRequest y ReplayServiceReport. La interfaz admite full-speed o step-by-step, filtros por rango, simbolo, venue y limite.

  • Casos de uso: testing de integracion, simulacion end-to-end, reproduccion de incidentes y parity checks.
  • Garantia actual: opera sobre raw ya capturado y respeta el orden reproducible del ReplaySource.
  • Hueco conocido: sigue siendo una superficie local del repo; no es aun un servicio remoto multiusuario.

Publication bus y contratos de entrega

El publication bus actual es un stream JSONL append-only bajo data/<env>/publication/. El comando publish_snapshot publica un record con env, venue, stream_type, symbol, published_at y payload curado o de snapshot.

El fichero delivery-contracts.json complementa ese bus dejando clara la semantica operativa por feed: freshness esperada, soporte de snapshot, replay, paper/live y modo de completitud.

Casos de uso recomendados

Research y backtesting

Consumir query_rows() y replay_service para evitar acceso ad hoc al layout de particiones.

Paper trading

Usar refresh_curated_store() seguido de load_snapshot() para bootstrap consistente antes de consumir updates.

Live operations

Publicar snapshots y usar delivery contracts para dejar explicitas freshness y completitud esperadas por consumer.

Informacion pendiente

  • La query historica sigue siendo local al repo; no hay aun un servicio remoto multiusuario ni control de acceso fuerte.
  • La capa curada es SQLite y suficiente para paper/local live support, pero no debe venderse como store distribuido de baja latencia general.
  • El publication bus sigue siendo file-based; su evolucion a bus de eventos real queda pendiente.
