Lectura de despliegue verificada

El repo muestra un despliegue local basado en Dockerfile + docker-compose.yml con tres servicios visibles: app, webUI y control-plane-worker. La UI de ingestion no se sirve desde el contenedor principal, sino desde un contenedor separado que comparte filesystem con el engine y solo consume telemetria y el read model desacoplado.

Proceso de despliegue local verificado

  1. scripts/docker-build.ps1 y docker compose build construyen la imagen base.
  2. docker compose up -d app control-plane-worker webUI levanta los tres servicios visibles.
  3. webUI escucha en http://127.0.0.1:8001/ui/overview y comparte bind mount del repo con los otros dos contenedores.
  4. Dentro de los contenedores, el repo queda montado en /workspace y el virtualenv se reutiliza en /workspace/.venv.

Relaciones de despliegue

  • Los tres servicios comparten el mismo bind mount del repo y el volumen poetry_venv.
  • app es quien puede producir market data, checkpoints y telemetria del runtime principal.
  • webUI y control-plane-worker comparten el telemetry path data/<env>/ui-telemetry y la base data/<env>/control-plane/control_plane.sqlite.
  • Solo webUI expone un puerto hacia el operador; el worker no publica interfaces de red.
  • La conectividad externa verificada en configuracion sigue apuntando a Binance por ws_base y rest_base; el control plane no reemplaza esa integracion.

Informacion pendiente

  • No se ha verificado un manifiesto de Kubernetes, ECS, Nomad o similar.
  • No se ha verificado una pipeline CI/CD que materialice despliegue automatizado mas alla de scripts locales y Compose.
  • No se ha verificado una separacion de volmenes distinta entre engine y control plane; la iteracion actual usa filesystem compartido del workspace.
  • No se ha verificado si prod se ejecuta dentro del mismo patron Compose, en host directo o en otra topologia externa.
