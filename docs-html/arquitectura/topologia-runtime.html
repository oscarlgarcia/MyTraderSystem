Lectura runtime verificada

La topologia runtime ya no es solo el proceso Python principal: el repo muestra un runtime cuantitativo principal mas un control plane web separado. El engine sigue siendo el unico que procesa market data y el control plane se limita a leer telemetria append-only y a escribir sobre un read model SQLite desacoplado.

Relaciones runtime verificadas

  • webUI llama a ReadModelBuilder.sync_once() antes de cada vista para materializar lineas nuevas de telemetria en SQLite.
  • El builder solo procesa ingestion_summary, ingestion_health, operational_alert y checkpoint_audit_ref.
  • control-plane-worker y webUI coordinan por command_requests y command_audit dentro del mismo SQLite de control plane.
  • La comunicacion observable entre contenedores es principalmente por filesystem compartido; no se ha verificado un RPC HTTP entre webUI y el servicio app.
  • El hot path de ingestion sigue fuera de la UI: dedup, persistencia y handoff viven en el engine principal.

Topologia por modo

ModoTopologia observadaDiferencia relevante
dryProceso Python principal, sin IO externo obligatorio, con control plane opcional encima.Apto para pruebas y CI; la UI puede mostrar poco estado si no hay telemetria.
paperEngine con market data live y ejecucion paper, mas control plane desacoplado.La UI ayuda a operar ingestion y recovery sin entrar en memoria del engine.
liveProceso principal mas estricto, con el mismo patron de control plane desacoplado.El repo endurece validaciones, pero no muestra una topologia distribuida distinta del control plane.

Huecos conocidos

  • No se ha verificado un scheduler, cola, bus de mensajes o microservicio independiente entre ingestion y el resto del pipeline; el control plane no cambia ese hecho.
  • No se ha verificado una topologia multi instancia con balanceo o HA para webUI o el worker.
  • La v1 sigue apoyandose en SQLite y filesystem compartido; PostgreSQL esta solo reservado como backend futuro.
