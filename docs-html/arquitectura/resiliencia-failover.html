Resiliencia y Failover

Escenarios de fallo, recuperacion y degradacion aceptable del runtime cuantitativo.

Diagrama base

Esta pagina mantiene la vista SVG ya publicada para no romper navegacion ni artefactos visuales existentes. En esta iteracion se prioriza completar escenarios operativos verificables sin introducir un nuevo diagrama.

Proposito

Documentar como resiste y se recupera la plataforma cuando fallan el serving de features, la evidencia operativa o la promocion de versiones. El alcance verificado en esta iteracion se centra en app.features y su operacion asociada.

Modelo de resiliencia verificado

SuperficieComportamiento verificadoEfecto operativoFuente
Serving de featuresFeatureServingService aplica politicas distintas por target. En paper puede degradar ante quality_flags; en live falla cerrado ante datos ausentes, invalidos o stale.La degradacion aceptable queda acotada y no se extrapola a live.app/features/serving.py
Frescura temporalEl runtime opera con available_ts <= decision_ts. La frescura aceptable es 300 s en paper y 30 s en live.Un vector stale no se considera servible para decisiones.app/features/definitions.py, app/features/validation_profiles.py, app/features/release_checks.py
Promocion de releasesLa publicacion se bloquea si fallan parity, stale count, invalid ratio o latencia; para live ademas exige readiness explicita.La recuperacion preferida es revertir version, no tolerar drift silencioso.app/features/release_checks.py, app/features/release_workflow.py, app/features/live_readiness.py
Evidence pipelineHay sondas verificadas de shadow, soak y concurrency, mas un manifiesto de evidencia y gates CLI.La continuidad depende de artefactos frescos, no solo de tests.scripts/feature_release_evidence.py, scripts/feature_shadow_validate.py, scripts/feature_serving_soak.py, scripts/feature_serving_concurrency.py, scripts/feature_live_go_no_go.py
RollbackEl workflow soporta rollback de release y restore controlado de la version previa; existe checklist dedicada.La respuesta a incidente esta orientada a volver a la ultima version conocida buena.app/features/release_workflow.py, scripts/feature_release_rollback_drill.py, docs/operations/feature_rollback_checklist.md
Disponibilidad de la APILa API HTTP del feature store expone /healthz y endpoints de consulta/insertado PIT.La disponibilidad observable del servicio existe, pero no sustituye un SLA formal.app/features/api.py, scripts/feature_store_server.py

Escenarios de fallo y recuperacion

EscenarioDeteccion verificadaComportamiento esperadoRecuperacion recomendada
Vector ausente o futuroServingResult.reason == "missing_or_future"La decision falla cerrada en paper/live.Revisar materializacion, repoblar el store y repetir smoke del serving antes de promover.
Vector stalestaleness_seconds supera la politica del target o stale_serves > 0 en gates.No se publica release y la decision no debe avanzar con evidencia vencida.Regenerar features y artefactos de observabilidad; no reciclar evidencia antigua.
Contrato training-serving invalidocontract_validation_failures o training_serving_contract_not_validatedBloqueo inmediato de serving estricto y de release.Registrar o corregir training_bundle, reconstruir metadata contractual y rehacer gates.
Shadow divergenceshadow_failure_budget_exceededlive pasa a no_go o exige rollback.Parar promocion, preservar artefactos y ejecutar rollback del feature set activo.
Soak o concurrency fallanArtefactos feature_serving_soak.json o feature_serving_concurrency.json con pass_ok=falseLa promocion no debe continuar.Investigar backend, latencia, contencion y repetir evidencia con ventanas frescas.
Feature release defectuosa ya publicadaGates post-promotion, auditoria o drift operativo detectan incumplimiento sostenido.Rollback obligatorio a la version previa.Ejecutar drill o rollback real con scripts/feature_release_rollback_drill.py y revalidar parity/contrato.

TargetDegradacion aceptableNo aceptableNota
