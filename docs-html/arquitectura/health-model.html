Lectura del modelo de salud verificado

El repo no expone un endpoint HTTP de health tradicional. En su lugar, el modelo de salud observable se construye combinando readiness reports, release gates, ingestion health, storage health y alertas operativas. El estado resultante no es binario puro; hay una degradacion intermedia antes del fallo total.

Estados de salud documentados

EstadoCriterio observableConsecuencia
SaludableCanaries, replay parity, storage y observability contract en PASS; sin alertas criticas.El runtime es confiable para operar segun el modo documentado.
ReadyReadinessReport.pass_ok = true y release gates sin bloques requeridos en FAIL.La promocion o ejecucion objetivo puede continuar.
DegradadoHay warning operativos, backlog de compactacion, skew alto, reconnect storms o drift que no rompen aun todos los gates.Se puede seguir ejecutando de forma condicionada, pero con menor confianza y mayor necesidad de vigilancia.
No ready / FailReadiness FAIL, release gates FAIL, gap irreparable, sink failure, compaction failure o exact recovery no verificado cuando es requerido.No debe promoverse ni asumirse continuidad saludable del sistema afectado.

Senales de readiness y liveness

CategoriaSenales verificadasUso
ReadinessReadinessReport.overall_status, pass_ok, resultados por paso en run_ingestion_readinessDetermina si el sistema esta listo para el target paper o live.
Liveness de streamsheartbeat_missed_total, reconnects_total, gap_irreparable_total, alertas heartbeat_missed y reconnect_stormEvalua si el conector sigue vivo y si el feed mantiene continuidad minima.
Salud de persistenciasegments_pending_total, compaction_lag_seconds, compaction_failures_totalEvalua si normalized storage sigue siendo fiable para recovery y consumo.
Salud semanticashadow_semantic_diff, vendor contracts, replay parity, exact recoveryEvita considerar sano un pipeline que sigue vivo pero produce datos semanticos incorrectos.

Criterios de degradacion

  • Warning: reconnects, skew o anomalies por encima de threshold warning implican degradacion controlada y vigilancia reforzada.
  • Critical: thresholds critical o alertas de severidad error implican estado no confiable para promotion o continuidad sin intervencion.
  • Storage degradado: backlog alto o compaction lag elevado pueden permitir continuidad temporal, pero reducen confianza para sesiones largas o recovery.
  • Fail inmediato: sink_failure, gap_irreparable, compaction_failure_detected o gates requeridos en FAIL deben tratarse como no ready.
