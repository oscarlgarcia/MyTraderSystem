Ingestion for Dummies

Explicacion operativa y funcional del modulo de ingestion para alguien que quiere entenderlo sin entrar primero al detalle del codigo interno.

Inicio / Preguntas Frecuentes / Preguntas Frecuentes Generales / Ingestion for Dummies

He revisado el código y los runbooks reales. La idea clave es esta: el módulo de ingestion no es solo “un scraper de mercado”. Es la primera fase del pipeline y su trabajo es capturar market data, validarla, normalizarla, guardarla y dejarla lista para que el resto del sistema la consuma. La entrada principal real está en ingestion, el runner aislado en ingestion-cli y el backfill histórico en los runbooks operativos de ingestion.

Su funcionalidad principal es:

  • conectarse a la fuente de market data
  • recibir trade y kline en tiempo real
  • aplicar resiliencia: reconnect, checkpoints, deduplicación y control temporal
  • persistir raw y normalized
  • materializar catálogo, calidad, service levels, snapshots y publication para consumidores downstream

Hoy, el scope operativo formal es:

  • paper: trade, kline
  • live: trade, kline
  • book: sigue fuera del scope formal; existe camino experimental, pero no debes tratarlo como soporte operativo estable

Qué funcionalidades tiene y para qué sirven

  • Ingesta live/paper: sirve para trading y paper trading. Recibe datos en vivo y abastece estrategia, riesgo, ejecución y portfolio.
  • Backfill histórico: sirve para research y backtesting. Descarga histórico soportado de trade y kline.
  • Persistencia raw + normalized: sirve para auditoría, replay y reproducibilidad.
  • Query histórica / snapshot / curated serving: sirve para bootstrap de consumidores, research y diagnósticos.
  • Quality / incidents / gap-fill / service levels: sirve para saber si el dato es confiable antes de usarlo en paper o live.
  • Control plane + worker: sirve para operar ingestion sin tocar el hot path, refrescar catálogo/calidad/serving y lanzar remediaciones.

Cómo debería funcionar día a día

Hay dos maneras de pensar ingestion:

  1. Como parte de la app completa.
    Esto es lo principal. Arrancas la app completa con python -m app y ingestion corre como primera fase del pipeline. Si le das un --max-events muy alto, el proceso se queda corriendo mucho tiempo. No es un daemon “puro” por sí mismo; normalmente lo dejas vivo con supervisor externo.
  2. Como herramienta aislada.
    Puedes ejecutar el runner puntual de ingestion con ingestion-cli. Ese sí es más “me conecto, recibo datos durante X tiempo y termino”. Es útil para pruebas, capturas puntuales o diagnósticos, no como happy path principal del sistema.

En operación diaria real:

  • para paper o live, lo normal es arrancar la app completa
  • dejarla corriendo todo el día con supervisor
  • tener en paralelo el control plane API y el worker
  • usar el cierre operativo al final del ciclo para validar catálogo, calidad, serving y publication

Comando principal para arrancarlo como ejecución diaria

Si quieres arrancar el sistema “como si hoy fueras a operar”, el comando principal no es el runner aislado: es la app completa.

Para paper, el happy path actual es el de paper_happy_path_runbook.md:

python -m app `
  --env dev `
  --mode paper `
  --max-events 1000000000 `
  --ingest-stream-types trade,kline `
  --feature-audit-path docs/validation/feature_decision_audit_paper.jsonl `
  --feature-consumer-name paper-runtime-strategy `
  --feature-consumer-kind strategy `
  --feature-dataset-id paper-runtime-btcusdt `
  --feature-schema-hash 27c5133305845d68af4062d03dec1c32d61c8d3083c35e382a4dd702e200fd18 `
  --feature-training-bundle-id legacy-legacy-paper `
  --feature-training-bundle-registry data/dev/feature-store/training-bundles

Para producción/live, el happy path documentado en production_happy_path_runbook.md usa el baseline más conservador, kline:

python -m app `
  --env prod `
  --mode live `
  --production-mode `
  --max-events 1000000000 `
  --ingest-stream-types kline `
  --feature-audit-path docs/validation/feature_decision_audit_live.jsonl `
  --feature-consumer-name prod-live-strategy `
  --feature-consumer-kind strategy `
  --feature-dataset-id live-runtime-btcusdt `
  --feature-schema-hash <PROMOTED_FEATURE_SCHEMA_HASH> `
  --feature-training-bundle-id <PROMOTED_TRAINING_BUNDLE_ID> `
  --feature-training-bundle-registry /var/lib/mytradersystem/data/prod/feature-store/training-bundles

Comandos para funcionalidades adicionales

  • Ingestion aislada puntual:
python -m app.ingestion.runner --env dev --duration 600
  • Ingestion aislada con fixtures locales:
python -m app.ingestion.runner --env dev --duration 30 --dry-run
  • Backfill histórico para research/backtesting:
python -m app.ingestion.backfill --env dev --symbol BTCUSDT --feed-type kline --start 2024-01-01T00:00:00+00:00 --end 2024-01-02T00:00:00+00:00 --interval 1m --batch 1000
  • Levantar la API operativa:
python -m app.controlplane.api --env dev --host 127.0.0.1 --port 8000
  • Levantar el worker operativo:
python -m app.controlplane.worker --env dev
  • Cierre operativo estandar de ingestion:
poetry run python scripts/ingestion_operational_cycle.py --target paper ...

Los detalles completos están en ingestion_operational_closure_paper.md y ingestion_operational_closure_live.md.
